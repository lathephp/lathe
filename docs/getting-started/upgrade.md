# Upgrade guide

This page is generated from the [changelog](changelog.md). Its API changes are the entries marked `[api]`, which change the public API: the classes and methods in the API snapshot, the artisan commands, the config keys, the route names and the JSON contract. Its behaviour changes are the other entries under Changed, which change what the panel does for your users.

It covers every release, newest first: each section holds the changes between a release and the one before it. Going up several releases, read each section from the release you run to the newest. Check each API change against your code before you update, and tell your users about the behaviour changes.

## From 1.0.0-beta.12 to 1.0.0-beta.13

### API changes

- `ExecuteAction::failed()` and `DeleteChunk::failed()` count a chunk's rows as failed once the queue gives up on it, and `PlanBulkRun::failed()` ends the run failed. `PlanBulkRun` and `DeleteChunk` set `$tries = 1`.
- `JobContext::isolate(Closure)` runs a callback and then puts back the user on the context's guard, the default guard and the locale. The `IsolatesJobContext` trait gives a job that middleware; `PlanBulkRun`, `ExecuteAction`, `DeleteChunk`, `ProcessImport` and `ProcessExport` use it.
- `JobContext` carries the starting request's `$ip` and `$userAgent`, two last optional constructor arguments, and `JobContext::server()` gives them as the server values of a job's own request.
- `RunStandaloneAction` is the job of a queued standalone action, and `ActionDispatcher::runQueuedStandalone()` runs it in the worker. `ActionDispatcher` gains the protected `queueStandalone()`, `dispatchRun()` and `runStandaloneHandler()`.
- Three English strings are new, for an app that translates the panel; none was renamed or removed: `Security settings are not available while impersonating.`, the answer of the password and two-factor routes while an admin impersonates someone, `This import has already started.`, the answer of an import step sent again, and `You may not list these records.`, what a relation picker and a relation filter in the filter bar say to a user who may not list the related records.
- `Timezone::storage()` names the zone a datetime column holds wall time in, the app's, and `Timezone::stored()` writes a moment as that text. `DateBucket::zoned()` and `DateBucket::offset()` take that zone as a last `$storage` argument, `'UTC'` by default. `AggregateQuery`'s protected `utc()` is now `stored()`. `RowCaster` takes the import's model as a second, optional constructor argument, and its protected `toDate()` a third, `$day`.
- `request()` of `@lathephp/core` sends a `FormData` body as it is, multipart, with no JSON content type, and sends the same body again after a password check.
- `@lathephp/core` takes React `^19.3.0` as its peer, as `@lathephp/ui` does, where it asked for exactly 19.3.0, so an app or plugin on a later React 19 installs both packages with no peer warning.
- `Filter::placement()` and `Filter::immediate()` are deprecated and stay in 1.x: each still returns the filter and still sets the `placement` or `immediate` key of its JSON, but the filter bar reads neither. Only `@lathephp/core`'s deprecated `FilterMenu` reads `immediate()`, and nothing reads `placement()`.
- `lathe:filter --custom` is deprecated and stays in 1.x: it still writes the filter class and its React component, and then says the option is deprecated, since the filter bar shows such a filter as a text key, not with its component.
- `FilterMenu` and `filter()` of `@lathephp/core` are deprecated and stay in 1.x: a custom page that renders `FilterMenu` still draws a component registered with `filter()`, as in 1.0.0-beta.12, while the filter bar of a Resource's list, a lens and a relation list shows such a filter as a text key. Both carry `@deprecated` in their types, so an editor strikes them through and `@typescript-eslint/no-deprecated` names each call. `lathe:doctor` still checks that a filter's component key is registered.

### Behaviour changes

- A relation picker and a relation filter's options answer 403 to a user who fails `viewAny` on the related Resource or whom its `canSee()` hides, where they listed its records: the picker of a belongsTo, morphTo, belongsToMany or tag field on a create or edit form, in an action's form and in a relation list's Attach dialog, the picker of a belongsTo or morphTo cell that edits inline on a Resource's list, a lens and a relation list, and a relation filter in the filter bar of a Resource's list, a lens and a relation list. For such a user a relation filter never lists the related records inline in the filter definition, even over a small table, and its chip names only a record they may `view`. The picker and the filter bar then say "You may not list these records." with no toast, and a tag field preloads its options only for a user who may list them. A picker still shows a saved value the user may `view`, so an edit form keeps it. A user who could pick records they may not list loses that picker; to keep it, give them `viewAny` on the related Resource. A hand-written filter whose `searchOptions()` reads another Resource's table must check the same itself.
- In `lathe/permission` 1.0.0-beta.13, released from this repository beside `lathe/lathe`, the permission plugin's role and permission fields show only to a user who passes `viewAny` on the Role or Permission Resource the plugin registered: for anyone else `RoleSelectField`, `RoleMultiSelectField` and `PermissionMultiSelectField` are left off the form, a posted value is ignored, and the panel answers their picker with 403, where a user who could edit users could grant any role or permission by its name.
- A belongsToMany field's pivot values meet their fields' rules on every write: a form checks each posted row under `{attribute}_pivot.{id}.{column}`, and the form, Attach and Edit pivot fill only the pivot fields the user can see that are neither readonly nor computed, where the form stored posted pivot values with no rule and wrote readonly and hidden pivot fields. A form that posts ids with no pivot row keeps each row's stored values. Detach and Edit pivot find the record in the related Resource's relatable scope, trashed records included, and answer 404 outside it.
- An import's `upsertBy()` and `skipDuplicates()` keys match only the rows the Resource's `editQuery()` lets the user edit, so a key held by a row outside that scope counts as new: the row is created, or fails if the column is unique. A `relationship()` column matches only the records the related Resource's `relatableQuery()` offers.
- Dashboards read a datetime column as wall time in the app's time zone, as forms and Laravel's own timestamps store it, so an app that does not run on UTC counts a record on the day and in the hour it was stored: an order placed at 23:30 on Nov 11 on an Asia/Dhaka app counts for Nov 11 in a value card and in a trend, for a user in Dhaka. The user's time zone still decides where a day starts. An app on UTC reads as before.
- A day group's subtotal, a date filter that cuts its days with `Timezone::dayBounds()` and a dashboard card's Open records link cut the same days as the dashboard on an app that does not run on UTC: `dayBounds()` gives a day's bounds in the app's time zone, where it gave them in UTC, so a query binds them as the column holds them. On an Asia/Dhaka app, Orders grouped by Placed day totals an order placed at 23:30 on Nov 11 under Nov 11, and the Placed filter for Nov 11 lists it.
- An import's `date()` column stores a datetime in the app's time zone, as a form does, where it stored UTC wall time; on an app that runs on UTC nothing changes, and on any other app the rows an earlier import stored are not converted, so they keep the UTC wall time it wrote. A column the model casts to `date` keeps the cell's calendar day: `2026-03-08` imported by a user in Asia/Tokyo stores March 8, where it stored March 7. A day group reads a `date:` cast with a format as a calendar day too.
- An export prints a column the model casts to `date` as its calendar day, `2026-03-08`, where it printed midnight moved into the user's time zone, `2026-03-07 16:00:00` for a user in America/Los_Angeles. A datetime column still prints `Y-m-d H:i:s` in the user's time zone, so a file exported and imported again by the same user leaves both unchanged.
- While an admin impersonates someone, the password change and every two-factor route of the Security page (turning two-factor on, confirming it, turning it off, its QR code, secret key and recovery codes) answer 403, so an impersonation never reads or changes the target's account security, and the Security page says so in place of its cards. Starting and stopping an impersonation forget the password confirmation, so the next action that asks for the password asks again, as the target and then as the admin.
- A form's unsent draft keeps no password field, and a reload restores the other fields with the password empty. The drafts and the palette's recent searches a browser keeps belong to the user who made them: signing out, signing in as someone else, and starting or stopping an impersonation clear them, across a reload too.
- Confirming the password and changing it on the Security page take 5 tries a minute per user, as the two-factor challenge does; the 6th answers 429.
- A standalone action that implements `ShouldQueue` queues, as any other `ShouldQueue` action does: the request answers with a queued run of one, the progress toast follows it, and the worker runs `handle()` once under one action event, which reads Finished or Failed. It ran inside the request.
- An import step sent again for an import that is waiting, running, imported or failed answers 422 "This import has already started." and leaves its counts as they were, where it ran the file a second time; a failed import still resumes from its run page, after its last saved chunk. Two resumes sent together queue the import once, and a step whose run could not be queued leaves the import as it was. A dry run can still be checked again and then imported.

## From 1.0.0-beta.11 to 1.0.0-beta.12

### API changes

- No public API changed since 1.0.0-beta.11: the classes and methods of the API snapshot, the artisan commands, the config keys and the route names are as they were, and the filters endpoint's JSON only gains each filter's `token` and `kind`, as the list's filters already carry, so an app updates with nothing to change in its code. One English string is gone, for an app that translates the panel; none is new or renamed: `Filters`, the relation list's button that opened its filter panel, which the list's filter bar and its Filter button replace.

### Behaviour changes

- A relation list on a record page searches and filters with the list's filter bar: one input for search and filters, a chip for each filter, and the Filter button with its count, in place of its search box and its Filters button and panel. Each relation tab keeps its own search and chips while the user stays on the page, so they stay while another tab is open and a reload clears them; the page URL never holds them, and a relation list has no saved views. A relation tab whose Resource has no filters and no search shows no filter bar. The `/` key no longer focuses a relation list's search; it focuses the filter bar on a Resource's list and on a lens.
- The filter bar's list of filters opens as a 320 px popover under the text cursor, so it follows the chips as they grow, and stays inside the bar when the cursor is near the bar's end, in a right-to-left panel too; it was as wide as the bar. On a phone it is the bottom sheet, as before. This holds on a Resource's list, on a lens and on a relation list.
- A group heading on a select field reads the option's label, as "Status: Pending", where it read the stored value, "Status: pending". A `titleUsing()` closure, date groups, relation columns and fields with no options keep their headings, and the group's key stays the stored value.
- When the server refuses an inline select's save, the editor comes back with its list closed and the cell's old value, so the message reads whole, where the open list covered it and the cell kept the refused value; Escape leaves the cell. A text or number cell keeps the refused draft to fix. This holds on a Resource's list, on a lens and on a relation list.

## From 1.0.0-beta.10 to 1.0.0-beta.11

### API changes

- No public API changed since 1.0.0-beta.10: the classes and methods of the API snapshot, the artisan commands, the config keys and the route names are as they were, and a list's JSON only gains `table.titleColumn`, so an app updates with nothing to change in its code. Three English strings are new, for an app that translates the panel; none was renamed or removed: `Filter` (the list's Filter button), `Change :field` (the spoken name of a cell that edits inline, as "Status: Paid. Change status") and `Waiting for a queue worker. Is one running?` (the import wizard and a queued run's toast).

### Behaviour changes

- The toolbar's Actions menu lists only standalone actions while no row is ticked, and shows no button when the Resource has none; ticking a row lists every action as before. This holds on a Resource's list, on a lens, on the Board, which ticks nothing, and in a relation list's pivot Actions menu. The Delete menu already showed only for ticked rows.
- On a list that edits inline, the view and edit links and the row menu at a row's end open on the first click. A link inside a data cell, such as a related record's name, still moves the cell cursor on the first click and opens on the second. This holds on a Resource's list, on a lens and on a relation list.
- A cell that edits inline shows a small chevron at its value's end, inside the badge or the meter of a select drawn as one, while the pointer is over the cell or the cell cursor is on it, on a Resource's list, on a lens and on a relation list. On a list and a lens a screen reader names the cell "Status: Paid. Change status". A read-only cell shows none.
- A lens page lists the Resource's tabs and the user's saved views in its views rail, before the lenses, with the lens marked current and the tab badges counted as on the list. A tab or a saved view chosen there opens the Resource's list.
- A lens's footer totals the lens's own fields that call `summarize()`, and a lens with none of them draws no footer. The footer showed the Resource's skeleton and never filled.
- A list or lens with filters shows a Filter button beside the filter bar. It opens the filter bar's list of filters, as a click in the bar does, and counts the active filters, as "Filter 2". A relation list keeps its Filters popover.
- From 1100 px the views rail of a list or a lens folds into the toolbar's Views menu whenever the table's columns would not fit beside it, so the columns read whole without scrolling sideways, as on Orders at 1280 px with the sidebar open; a list whose columns fit keeps the rail open.
- The cards of a dashboard, of a Resource's list, of a lens and of a record page read their values from the widget endpoints through the panel's query cache, which keeps a value fresh for 60 s: going back to a page within 60 s shows its cards at once with no request, and after 60 s shows the kept values while it fetches them again. Refresh, a range change, a run action and a filter change still fetch. A dashboard page no longer sends each card's value as a deferred prop, so it asks for them after it paints, one request per card. The exported `WidgetGrid` and `WidgetCard` read through the same cache, so the cards of a plugin's custom page do too.
- A record page shows only the cards marked `onlyOnDetail()`, as the widget docs describe; the other cards of the Resource show above its list and no longer repeat on each record. `WidgetList::visible($request, true)` returns only the detail-only cards, so `GET .../widgets?resourceId=`, `useWidgetList` with a `resourceId` and the testing kit's `widgets(['resourceId' => ...])` list only them. A card meant for both places is listed above the list only; mark a card `onlyOnDetail()` to keep it on the record page.

## From 1.0.0-beta.9 to 1.0.0-beta.10

### API changes

- No public API changed and no English string is new, renamed or removed since 1.0.0-beta.9, so an app updates with nothing to change in its code or its translations.

### Behaviour changes

- The top bar's search shows as its icon button, as on a phone, whenever the top bar is narrower than about 760 px: in a window narrower than about 1,016 px with the sidebar open, or about 808 px with it collapsed. It showed the search box from 768 px up. Ctrl+K and ⌘K open search as before.

## From 1.0.0-beta.7 to 1.0.0-beta.9

### API changes

- `WidgetCard` takes its columns from the width of the nearest container, not the window's, so a custom page that puts cards in a grid of its own makes that grid a container (Tailwind's `@container`), as `WidgetGrid` does; in a grid that is not one, every card keeps its phone layout at any width.
- No English string is new, renamed or removed since 1.0.0-beta.7, so an app that translates the panel has nothing to add.
- A plugin can limit its settings to some of the users who may use it with `canSeeSettings(Closure $callback)` or `canSeeSettingsWhen(string $ability, mixed $arguments = [])`. The rule gates `GET` and `PUT` on the plugin's settings API, its settings page and the automatic Settings link, each answering `403` or leaving the link out for a user it refuses. It only narrows `canSee()`: a user `canSee()` denies is refused whatever the settings rule says, and without a settings rule a plugin's settings follow its `authorize()`, as before. A plugin with neither a settings rule nor `canSee()` or `canSeeWhen()`, and no `authorize()` of its own, lets every panel user read and change its settings. A `menu()` list is kept as written, even an item named Settings, and `lathe:plugins` lists the plugin as an admin sees it.

### Behaviour changes

- The cards of a dashboard, of a Resource's list and of its record page take their layout from the width of their grid, not the window's: beside the sidebar, from 768 px up to about 1,070 px the cards sit as on a phone, value and progress cards of a third or less two across and the rest across the row, where four quarter cards were squeezed to 101 px at 768 px and cut every title and number. A collapsed sidebar gets the 12 columns sooner.

## From 1.0.0-beta.6 to 1.0.0-beta.7

### API changes

- New English strings since 1.0.0-beta.6, for an app that translates the panel; none was renamed or removed: `Waiting`, `Running`, `Finished` and `Failed` (the Action Events list's Action Status filter), `:action: changed :fields` (a History entry of an action run, as "Cancel order: changed Status") and `This record is attached more than once.` (Edit pivot or Detach on a record attached twice to a pivot table with no id column).
- A value card's number range counts calendar days in the user's time zone, today and the N - 1 days before it, compared with the N calendar days before those, so its total matches a trend card's for the same range. It counted the last N times 24 hours back from now, so at 7 days an order placed late on the eighth day ago counted in the card and not in the trend. `TODAY`, `YESTERDAY`, `THIS_WEEK`, `MTD`, `QTD`, `YTD` and `ALL` keep their windows, and `AggregateQuery::value()` is unchanged.
- A date filter can name the column it narrows with `DateFilter::column()`, null by default. When it names one, the Open records link of a dashboard card dated by that column opens the list with the filter set from the card's first day to its last, `filter[key][from]` and `filter[key][to]`, so the list holds the rows the card counted. This works for a value card with a number range and a trend by days, weeks or months; a trend by minutes or hours, a named range such as `MTD`, a card dated by another column and a card with its own `link()` keep their links.
- A range filter takes strict sides, `filter[key][gt]` and `filter[key][lt]`, compared with `>` and `<`; `min` and `max` stay inclusive, so an existing link or saved view keeps its meaning. A filter `filterable()` generates applies them on the column as stored, so a cents column compares `gt=150000` with 150000 cents. `RangeFilter::normalize()` returns `gt` and `lt` beside `min` and `max` only when the request sends them, and only for a filter whose `$strict` property is true: a filter `filterable()` generates sets it, unless it has a `filterable(fn ...)` callback, which keeps receiving `min` and `max` only. A `RangeFilter` subclass takes them once it sets `protected bool $strict = true` and reads them in `apply()`; until then it answers 422 to `gt` or `lt`, and the filter bar writes its `>n` and `<n` as `min` and `max`, chips "≥" and "≤" as before. Each range filter's definition in `filters.available` carries `strict`.
- A value card that averages, or takes the minimum or maximum, says "No earlier data to compare with." when the days before its range hold no rows, as a count or a sum card does; Average order at 12 months showed no line. The `previous` of such a card's response is 0 where it was null. A card at `ALL` still has a null `previous`, and `AggregateQuery::value()` and `valueBetween()` still return null for an average of no rows.
- An action run's events show the values the action changed on each record under Original and Changes, where both were always empty. The records are read again once per 200 after the run; the update timestamp, hidden attributes and password or token attributes are left out, and a record the action did not change keeps both empty. A record's History card names the fields such a run changed, as "Cancel order: changed Status": the `title` of an `action-ran` entry from `GET .../history/latest` is that text where it was the action's name.
- An action whose `handle()` returns `ActionResult::danger()`, inline, standalone or in a queued chunk, leaves its action events Failed, with the message under Exception, where they read Finished: the `status` of those `lathe_action_events` rows is `failed` and their `exception` the message. The response is unchanged: HTTP 200 with the danger toast, and the row counts as run, not failed.
- A `belongsToMany` or `morphToMany` field with `withCount()` shows the related count in its index column, loaded in one query for the page; the column was empty. `BelongsToManyField::resolve()` returns that count as an int when the record carries `<relation>_count`, and the cell's `value` is the count where it was null.
- Edit pivot, its form and Detach work on a `belongsToMany` or `morphToMany` whose pivot table has no id column, where they answered 404. A relation panel's row carries `pivot_id` only when the pivot table has an id column; the server finds a row of a pivot table with none by its related key and ignores any `pivot_id`, and a record attached to it twice answers 422 on `related_id` with "This record is attached more than once." and changes nothing.

### Behaviour changes

- In the filter bar, `total:>1500` and `total:<1500` leave out an order of exactly 1,500, and their chips read "Total: > 1,500" and "Total: < 1,500"; `total:1000..1500` and a bare `total:1500` still include their ends. A date filter's `>` and `<` still include the date.
- On a dashboard, a card with no `ranges()` of its own receives the header's range as `$request->query('range')`, so a bar, partition, pie or progress card that reads it follows the picker; it received no range and showed whatever its code fell back to, with nothing on the card to say so. A card with `ranges()` is unchanged.

## From 1.0.0-beta.5 to 1.0.0-beta.6

### API changes

- The panel home (`/lathe`) sends a user who may not see the main dashboard to the first dashboard they may see, else to the first sidebar page they may open, and answers 403 only when they may open nothing. Sign-in, the brand link and starting or stopping an impersonation land there too. `DashboardController::__invoke()` returns `Response|RedirectResponse`.
- Export and import download links are relative signed URLs checked with `signed:relative`, so a link the queue worker built works at whatever address the panel is opened on, not only at `APP_URL`. `Export::downloadUrl()`, `Import::errorsUrl()`, the `download_url` of `GET .../api/exports/{export}` and the `errors_url` of `GET .../api/imports/{import}` return a path with no host, and so does the `url` of the Download button in the `ExportReady` notification and of Download failed rows in `ImportComplete`. A channel added with `Lathe::notificationChannels()` that sends them outside the panel, such as mail or Slack, puts its own host in front with `url()`. A link signed as absolute for these routes, including one issued before the upgrade, is refused; the next status poll or a new export gives a fresh one.

### Behaviour changes

- In a `dependsOn()` callback, `FormData::get()` returns a `belongsTo` field's key, not the picker's `{value, display}` array, so `Product::find($formData->get('product'))` finds the record. A callback that read `['value']` reads the key directly.
- Value and trend cards offer the dashboard's ranges by default, 7 days, 30 days and 12 months (they were 30, 60 and 365 days, and 30, 60 and 90 days), and still start at 30 days, so a dashboard set to 7 days or 12 months no longer shows "Last 30 days" on its cards. A card with its own `ranges()` is unchanged.
- `TrendResult::transform()` changes the trend's points and series as well as its headline, so `->transform(fn ($cents) => $cents / 100)` plots dollars.
- Extension CSS built through the Lathe Vite plugin imports Tailwind's theme as a reference: `@import "tailwindcss"` defines no `:root` variable that could override the panel's (an app extension turned the panel's Archivo into the system font), and with no `source()` of its own it scans the extension's folder: in an app the boot file's folder (`resources/js/lathe`), not the whole app, and in a plugin its whole folder. `@lathephp/core/tokens.css` is a reference theme too. Hand-written CSS in an extension that read one of Tailwind's default variables, such as `var(--color-red-500)`, must define it.
- `Field::heading()` and `Field::hidden()` are compact, so a form draws no label row and no Optional mark for them.
- An action's `->icon('mail')`, a kebab-case Lucide name, draws the same icon as `->icon('Mail')`. `Field::icon()` and a badge's `withIcons()` given a name the field icon set does not draw log one browser console warning that names it; the fields docs list the 27 names the set draws.
- A column's `indexWidth()` holds: its header and cells are that wide at least and at most, where the cells' 320 px cap could widen it before.
- A list with no inline-editable cell, such as Action Events, follows a link in a cell, such as a related record's name, on the first click and still moves the cell cursor there. A list that edits inline keeps the beta.5 rule: the first click moves the cursor and the link opens once its cell holds it.
- The trashed-only view of a soft-deleting list (`trashed:only`) draws no Soft Deleted badge, since every row in it is deleted; a view that mixes live and deleted rows keeps it.
- An inline save, a Board move included, drops the saving user's cached sidebar badge of that Resource, so a badge such as a count of pending orders shows the change on the next read instead of after its TTL.

## From 1.0.0-beta.4 to 1.0.0-beta.5

### API changes

- Each filter in the index payload's `filters.available` carries `token`, its key in the filter bar, and `kind`, the value that key takes: `select`, `multiple`, `range`, `date`, `boolean`, `relation` (a remote picker) or `text`. The token is the filter's `key()`, except that a `filterable()` field's filter goes by its label in snake case (`total` for Total) unless that clashes with another filter's key.
- Each saved tab in the index payload's `tabs.saved` carries its search as `q`, and `filters.labels` names the remote values of the saved view `?saved_tab=` opens, so the filter bar draws an open saved view's filters and search as its chips and text; changing one leaves the view and writes every chip to the URL.
- A select opts into a status meter with `meter(except: [...])`. The payload carries the tick values as `meter`, and a meter with fewer than 2 or more than 5 ticks throws a `LogicException` naming the field when `fields()` builds. The workbench's order status leaves Cancelled out of the ticks:

  ```php
  Field::select('Status')
      ->options(['pending' => 'Pending', 'paid' => 'Paid', 'shipped' => 'Shipped', 'cancelled' => 'Cancelled'])
      ->meter(except: ['cancelled']);
  ```
- `->board('<field>')` on a Resource's definition shows its list as a Board too, one column per option of that index field in declared order, plus a No value column when the field is nullable. The field must be an inline select with at most 12 inline options; anything else throws a `LogicException` naming the field when the Resource boots, and a subclass that drops the field calls `->board(null)`. The index payload carries `table.board`, `{field, noValue}`, or `null` on a lens, without a board, or when the user cannot see the field.

  ```php
  return $definition
      ->model(\App\Models\Order::class)
      ->board('status');
  ```
- A list with a board opens in the layout its URL names, `?layout=board` or `?layout=table`, else in the one the user chose last on that Resource, else as the table. `PUT .../resources/{resource}/layout` with `{layout}` saves the choice per user (404 for a Resource without a board), and the index sends the layout it opened in as `table.layout`, always `table` on a lens or without a board.
- `GET .../resources/{resource}/board?column=<option>&page=<n>` returns `{rows, hasMore}`: one page of 25 cards of a Board column, each row shaped as in `table.rows`, in the list's sort. `&offset=<n>` in place of `page` starts at that card, which the Board's Show more sends so a card moved out of the column skips none. An empty `column` is the No value column, allowed on a nullable field; an unknown column, a bad page or offset, or one at the count cap or past it is 422, and a Resource without a board is 404. `GET .../board/counts` returns `{columns: [{value, count}]}`, one capped count per column in option order with `null` last on a nullable field. Both read the index's own query keys (`filter`, `q`, `tab`, `saved_tab`, `sort`).
- `GET .../{id}/preview` serves the preview panel. With an empty `fieldsForPreview()` it returns the record's detail fields without its relation lists (a BelongsTo or MorphTo name stays), so every Resource has a preview; `showOnPreview()` no longer narrows it, a field marked `showOnPreview()` or `onlyOnPreview()` joins it, and `hideFromPreview()` still drops a field. The reply adds the record's `abilities` and its detail `actions`. Each user's panel is open or closed per Resource: `PUT .../resources/{resource}/preview-panel` with `{open}` saves it, and the index sends it as `table.previewOpen`.
